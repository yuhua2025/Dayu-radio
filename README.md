# Dayu-radio · ESP32-S3 网络收音机

基于ESP32S3的桌面网络收音机。全功能可配置：手机网页配网、在线选台、调音量、改电台表、切换频谱风格；屏幕实时显示台名/歌曲/时间/信号/电量。

原始固件的电台表从厂商 bin 里逆向提取，这一版是**完全重写**的源码实现。

```
Dayu-radio/
├── stations-qtfm.m3u    62 个台的播放列表（电脑上可直接试听）
├── docs/                界面截图
├── prebuilt/            预编译镜像（见「预编译镜像」）
├── tools/               字模生成、镜像打包、抓屏、换台耗时探针
└── dayu_radio/          Arduino 工程（目录名必须与 .ino 同名）
```

## 硬件

ESP32-S3（16MB Flash / 8MB OPI PSRAM）、ST7789 240×240（SPI）、I2S 功放、3 个按键、3.7V 锂电。

| 用途 | GPIO | 说明 |
|---|---|---|
| LCD SCLK / MOSI / DC / CS / RST / BL | 9 / 10 / 8 / 14 / 18 / 13 | LovyanGFX，SPI2，40MHz |
| I2S BCLK / LRC / DOUT | 15 / 16 / 7 | ESP32-audioI2S 输出 |
| BOOT 键 | 0 | 短按换台，长按 8 秒清配网 |
| 音量 + / − | 40 / 39 | 按住连发 |
| 电池电压 | 17 | 锂电经 100k+100k 分压（1/2），**注意是 ADC2** |
| 充电检测 | 38 | 高电平 = 充电中，下拉输入 |

> ⚠️ GPIO17 在 S3 上属于 ADC2，与 WiFi 驱动共享。实测（core 3.3.12）能稳定读数，但代码按"不可靠"处理：16 次平均，落在 1.2~2.6V 才认，否则沿用上次值，避免电量在 100%/0% 之间乱跳。

## 编译与烧录

用 arduino-cli，FQBN 必须带这些选项：

```bash
FQBN="esp32:esp32:esp32s3:FlashSize=16M,FlashMode=dio,PSRAM=opi,PartitionScheme=huge_app,CPUFreq=240,USBMode=hwcdc,CDCOnBoot=cdc"

arduino-cli compile --fqbn "$FQBN" --build-path build .
arduino-cli upload  --fqbn "$FQBN" --input-dir build -p /dev/cu.usbmodemXXXX .
```

依赖：
- `ESP32-audioI2S-master`（3.4.7）—— **需要打补丁，见下**
- `LovyanGFX`（1.2.35）

### 依赖库补丁（必做）

`Audio.cpp` 的 `setSampleRate()` 默认无条件重配 I2S 时钟。44.1k 与 48k 台切换时 I2S 断流，外部功放休眠唤醒会"啪"一声——**软件静音盖不住，因为它发生在模拟域**。补丁做两件事：

```cpp
bool Audio::setSampleRate(uint32_t sampRate) {
  ...
  if (sampRate == m_i2s_items.sampleRate) return true;   // ① 同采样率直接返回，别碰 I2S
  m_i2s_items.sampleRate = sampRate;
  if (m_output_sr != SR_ORIGIN) {                        // ② 固定输出率时只更新重采样器
    m_resampler.phase = 0;
    m_resampler.phaseStep = ((uint64_t)sampRate << 32) / m_output_sr;
    m_resampler.g_lpCoeffs = makeButterworthLPF_Q31(sampRate);
    m_resampler.lpLeft = {}; m_resampler.lpRight = {};
    IIR_calculateCoefficients();
    return true;
  }
  reconfigI2S(); IIR_calculateCoefficients(); return true;
}
```

配合固件里的 `audio.setOutputSampleRate(Audio::SR_48000)`，I2S 时钟从此永不断流。**重刷库后必须重打补丁。**

## 使用

### 按键

| 操作 | 效果 |
|---|---|
| BOOT 短按 | 下一个台（按下瞬间响应）|
| 连续快按 | 合并成一次跳转（按 3 下跳 3 个台，只连一次）|
| BOOT 长按 8 秒 | 清除 WiFi 配置并重启（中途松手立即取消）|
| 音量 + / − | 调节（按住连发）|

### 配网

首次开机自动开热点 **DayuRadio**（无密码）：
1. 手机连上热点，浏览器打开 `192.168.4.1`（多数手机会自动弹门户）
2. 点选家里的 WiFi、输密码 → 连接
3. 成功后热点自动关闭，手机切回家里 WiFi，访问屏幕上显示的 IP

连不上会逐条给原因（找不到网络 / 密码不对 / 信号太弱），不会像原版固件只丢一句英文。

**配网页加载**：实测页面 4.7KB，设备侧 **65~95ms**（首字节 28~47ms，Wi-Fi 直连实测）。
做过四件事保证这个数字：① HTML 响应按 1KB 分块流式发送（浏览器不必等整包到齐）；
② 配网模式下主循环跳过频谱/电池/音频状态机，只喂 HTTP（整屏重绘也从 1.5s 放宽到 5s，
那 30ms 的 SPI 推送本来在跟 HTTP 抢时间）；③ 热点固定信道 6（默认信道 1 在楼道里最挤）；
④ 未知路径一律 302 到配网页 —— iOS/Android 的系统探测拿到 302 就会自动弹门户，
用户不用自己记 192.168.4.1。

从"点连接热点"到"看到页面"的总时间里，设备只占一点点，大头是手机侧的关联 + DHCP +
系统门户探测（约 3~8 秒），这部分不可控。

**配网成功之后**：热点 8 秒后自动关闭（原来留 60 秒，用户会以为"卡住了"），设备立即开播、
屏幕切回播放界面。注意"配网模式让路 HTTP"只对**还没配好**的状态生效 ——
一旦开播就必须恢复完整主循环喂音频，否则声音出不来（踩过一次）。

**老固件升级**：首次运行会自动把旧 WiFiManager 存在系统 NVS 里的凭据迁移过来，不用重新配网。

### 网页设置

浏览器打开 `http://<设备IP>`：

- **播放**：上一台 / 下一台 / 台号下拉（62 个台）/ 音量滑条
- **频谱**：5 种样式即时切换（热力柱、镜像双翼、声纹波形、LED 点阵、彩虹柱）
- **自定义电台**：每行 `名称|URL`，保存立即生效（不重启）
- **系统**：WiFi 信号与 IP、重新配网、重启、清除 WiFi

### 电台表

三层拼装：原厂蜻蜓FM 台（当前 62 个可用，`stations-qtfm.h`）→ 内置公共流（当前为空）→ 自定义台（网页填 `名称|URL`）。

台号查法：`qtfm.cn` 搜台名 → 进频道页 → URL 末尾数字，拼成 `http://lhttp.qtfm.cn/live/<台号>/64k.mp3`。

**数据流**：`audio` 解码 → `audio_process_i2s()` 弱钩子取 PCM（供频谱）→ I2S 功放。

## 关键设计

### 1. 预取代理：换台从 1 秒降到 150ms

放 A 台时，后台任务用另一个 socket 把 B 台连好、请求头收好、body 攒 32KB（约 4 秒音频）。按 BOOT 时 `audio` 连本机代理，代理把存粮直接吐过去——跳过服务器 150~1650ms 的预热。

- 代理是独立 FreeRTOS 任务（核 0，优先级 2），非阻塞状态机，不占主循环
- 预取放了 60 秒没用会重暖一条新的（CDN 长连接会被掐）
- 接管有 1.5 秒"宽限期"，否则会出现"刚收到连接就把它清了"的竞态
- `config.h` 里 `USE_PREFETCH_PROXY 0` 可退回直连对比

### 2. 起播垫：用 1~2 秒的等待换"出声之后不卡"

音频库只要内缓冲过 18KB 就会出声——那是"能解出第一帧"，不是"够放下去"。CDN 一个突发填满就开口，突发一停立刻断粮，用户听到的就是"刚出声就卡一下"。

所以起播前先攒存粮，攒够才放行：

| 参数 | 值 | 折合 64kbps 时长 |
|---|---|---|
| 预取存粮 `PRE_TARGET` | 48KB | 约 6 秒 |
| 命中门槛 `PRE_MIN_READY` | 40KB | 约 5 秒 |
| 实时路径起播垫 `CUSH_TARGET` | 40KB | 约 5 秒 |
| 攒垫最长等待 `CUSH_MAX_MS` | 2 秒 | 到点有多少喂多少 |
| 断流看门狗 `UP_STALL_MS` | 6 秒 | 存粮够撑，别自己掐自己 |

**断流看门狗必须跟着放宽**：存粮 5 秒 + 看门狗 3 秒 = 手里还有 3 秒歌却主动断线重连，等于我们自己制造卡顿。现在 6 秒才掐。

这套参数是用户明确选择的取舍："宁可起播多等 1~2 秒，也别中途卡"。实测换台 279~285ms（预取命中）、1362ms（冷启动），静听 150 秒 0 次断流。

### 3. 换台音质：按下即静音，出声后渐入

按下瞬间 `setVolume(0)`（不渐变），掐流前排空 150ms（等库内 gain_ramp 落底、解码器残留样本冲出 DMA），新台出声后 1.1 秒爬回用户音量。配合固定 48kHz 补丁，破音与爆音全消。

### 4. 断流看门狗

网络差时有两层卡死风险，都要堵：

**① 代理侧**：上游 CDN 断流时 `audio.loop()` 会干等 socket，主循环彻底冻结。代理侧 3 秒无数据就主动掐断，让上层走 EOF 重连。死台黑名单 1 分钟（别设 5 分钟，会"一次跳过 6 个台"）。

**② 音频库侧**：`audio.loop()`/`connecttohost()` 内部读 socket 要等超时才返回，超时值就是主循环最坏卡死时长。原来 `setConnectionTimeout(4000, 8000)` —— 网络一拥塞就冻 8~12 秒，屏幕不动、按键全不响应（"网络不好就卡死"的真身）。现在 `(2500, 1500)`：64kbps 流每 100~200ms 来一个包，1.5 秒收不到基本就是断了，交给重连更快。卡死上限压到 4 秒。

**③ 保底**：独立看门狗任务盯主循环心跳，12 秒没跳动就强制重启（正常慢流程如连跳死台、预热链都会主动喂心跳，不会误杀）。防的是"万一还有没堵住的阻塞路径"——宁可重启一次，也不要永久死机。

**④ 空播看门狗（"开机没声音，按一下下一个台才有"）**

"出声"的判据原来是 `audio.getBitRate() > 0`。问题是这个库在内缓冲只有 128 字节时就会建解码器、解析出 MP3 帧头，码率立刻 > 0，而真正出声还要再攒够 18KB —— 码率 > 0 只代表"摸到了帧头"。一旦流僵在"建了解码器、一个样本都没出"的位置（CDN 半连接、代理刚吐完头就断供……），界面显示"播放中"、淡入也做完了，喇叭却全静音；更糟的是它已被判成"已出声"，9 秒放弃和自动跳台两条恢复路径全部不触发，只能人工按一下换个台。

现在判据换成**真实送进 I2S 的样本数**（`spectrumSampleCount()`，来自频谱同一个 PCM 钩子 —— 音量 0 时送的是全零样本，计数照样涨，所以"有没有数据"和"音量多大"被彻底分开，静音坡道不会误判）。再加一层空播看门狗：以为在播却连续 4 秒没有样本，就 `audio.stopSong()` 重连（等价于手动换台再换回来，实测 4.0 秒侦测、4.8 秒重新出声）；重连两次仍无数据才换台。慢网络下等待时间翻倍（4s→8s），不会把"首包就要 5 秒"的台冤判成死台。

顺带修掉一个开机竞态：代理的 `listen` 原来在代理任务第一行才建，而 `proxyBegin()` 建完任务就返回，开机首播可能撞上"端口还没开"，直接退回直连、少一层缓冲。现在监听在 `proxyBegin()` 里同步建好。

### 5. 频谱

数据来自音频库的 weak 钩子 `audio_process_i2s()`（音量/增益之后的 48kHz 输出），**不必改库文件**。80ms 一帧：256 点自写 FFT → 24 个对数频带（187Hz~10.5kHz）。

**必须有自动增益**：音乐是宽带信号，单频带幅度实测在 -90~-40dB 之间随节目浮动，固定映射窗口必然"有的台趴着、有的台顶满"。参考电平快升慢降自适应。

绘制画两份：小 sprite 推屏（80ms 局部刷新，不整屏闪）+ 整屏 sprite 同步一份（整屏刷新自带、串口抓屏可见）。**别改用直写 lcd**——直写内容会被 400ms 一次的整屏刷新盖掉，且抓屏根本看不见。

### 6. 电池

百分比走锂电 OCV 分段曲线（3.3V 空 ~ 4.2V 满，13 点插值），**不要用 3.0~4.2 线性**：锂电 3.7~3.9V 是平台区，线性会把"一半电"显示成 30%。

充电中电压会虚高 0.1V 左右（测的是充电电压），显示 100% 属正常，拔线后自动回落。

### 7. 按键

全部轮询，**不用 GPIO 中断**。中断判据（"必须出现 80ms 稳定高电平" + 中断里判方向）对真按键的弹跳是灾难，会整批吞掉按压——而仿真按键测试永远通过，极难发现。

长按判据是"实际采到的连续按住时长"，每个采样间隔最多计 200ms：主循环卡住的那段等于不计时。宁可让人多按一会儿，也绝不能把卡住的时间算成"用户按住了"——那会直接删掉 WiFi 密码。

### 8. 屏幕稳定性（开机画面偶发半屏）

两个独立原因，都要治：

**① 开机阶段被"频谱块"挖掉一块**：`spectrumSetStyle()` 在 setup 里恢复上次风格时默认会重绘，
而它内部的 `s_panel.pushSprite()` 会直接往屏幕上推一块 224×74 的频谱 —— 那时屏幕上是开机画面，
看起来就是"开机画面缺一块 / 停在半屏"。现在 setup 里传 `repaint=false`，只设参数不画。

**② SPI 40MHz + PSRAM sprite + DMA 偶发传不完**：整屏 sprite 在 PSRAM，`pushSprite` 走 DMA
从 PSRAM 读，40MHz 下偶尔传输不完整 —— 上半屏是新画面、下半屏还是上一帧。降到 **27MHz**，
代价只是整屏刷新 30ms→45ms（这个界面 400ms 重绘一次，无感）。

### 9. 网页

- 扫网用 `WiFi.scanNetworks(true)` **异步**轮询：同步扫要阻塞 2~4 秒，会卡断音频
- 网页换台是**异步**的：API 立即回 `ok`，换台由主循环执行。同步做会让浏览器转圈几秒甚至超时
- 配网失败不重启：起热点等用户操作，连上自动开播

### 10. 网络流畅度指示（右下角三圆点）

指标 = 代理层"距上次从上游读到音频数据"的间隔（`proxyFeedGapMs()`），
10Hz 采样 + EMA（时间常数约 0.5 秒）平滑，三档：<600ms 绿（流畅）/ <1300ms 黄（一般）/ 更差 红（卡），点亮 3/2/1 个圆点。
用圆点而不是竖条，是为了和左上角的 WiFi 竖条区分开：前者说"流顺不顺"，后者说"信号强不强"。

**阈值是实测标定的**：正常播放时 CDN 按突发发包，实测 gap 在 3~400ms 之间波动（19 个样本全为流畅档）；
断供超过 1 秒解码器存粮才真的见底。所以"流畅"档必须放宽到 600ms——若按直觉设 260ms，正常播放就会常亮黄灯，指示器变成狼来了。

吐预取存粮/起播垫阶段上游不供数，`proxyFeedGapMs()` 返回 0，指示器不显示（换台中同理）。

## 网页 API

| 路径 | 说明 |
|---|---|
| `GET /` | 未联网或从热点访问 → 配网页；否则设置页 |
| `GET /scan` `GET /connect` `GET /netstatus` | 配网三件套（scan 返回 `{"pending":1}` 时需重试）|
| `GET /api/status` | JSON：台号/台名/歌曲/音量/信号/频谱风格/电量/充电/IP/固件 |

## 故障排查

| 现象 | 处理 |
|---|---|
| 开机黑屏但背光亮 | `config.h` 里 `LCD_INVERT` / `LCD_ROTATION` 试反 |
| 连不上 WiFi | 看串口 `[NET] 连接失败 code=`，或长按 BOOT 8 秒重新配网 |
| 网页打不开 | 设备 IP 可能变了（DHCP），看串口 `[wifi] <IP>` |
| 某个台一直跳过 | 该台源失效，网页设置页编辑电台表 |
| 电量显示 `--%` | ADC 读数异常，串口 `e` 看引脚电压是否在 1.5~2.2V |
| 换台有爆音 | 检查 Audio.cpp 补丁是否还在（重刷库会丢）|
| 频谱不动 | 静音或换台中；串口看是否有 `[play] 出声` |
| 开机偶尔没声音 | 已修（出声判据改成真实样本 + 4 秒空播看门狗自动重连）；串口会打 `[play] N 号台 ...没有音频数据 → 自动重连` |
| 网络差时界面卡住、按键无响应 | 已修（音频库超时 4s 上限 + 12s 看门狗重启）；若仍偶发，串口看是否有 `[wdt]` 或 `[proxy] 断流` |
| 串口没输出 | USB CDC 在烧录后会短暂消失又回来，等 3 秒；换根数据线 |

## 已知限制

- 换台期间（≤4 秒）网页请求会排队等待，属架构性（换台占用主循环），页面 2 秒轮询会自愈
- 网络刚起来时前几个台可能连不上（CDN 边缘冷启动），会自动跳过
- 充电中电量显示偏高（充电电压），拔线后回落
- 单节锂电无充放电管理 IC，请勿边充边大音量长时间使用
